# Bloodtrack Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** A Nuxt v4 web app for tracking a Blood Bowl-style league: admin sets up rounds of paired matchups; each player logs post-match stats (result → league points, touchdowns, casualties); the app computes standings over the whole league with tiebreakers TDs then casualties.

**Architecture:** Nuxt 4 full-stack app. Server API routes (Nitro) persist league data in SQLite via `node:sqlite` (Node 24+ built-in, zero deps). Pure scoring logic lives in `shared/league.ts` so it runs on both client and server and is unit-testable without Nuxt auto-imports. Client state: current identity stored in `localStorage` (no auth). UI is Tailwind CSS v4 + DaisyUI 5 components.

**Tech Stack:** Nuxt 4, Tailwind CSS v4 (`@tailwindcss/vite`), DaisyUI 5, pnpm, Node ≥24 (`node:sqlite`), vitest.

**Environment notes:**
- Project root: `/workspace/Bloodtrack`.
- Check toolchain first: `node -v` (need ≥24), `corepack enable && corepack prepare pnpm@latest --activate` if `pnpm -v` fails.
- `shared/` pure-logic tests never touch Nuxt auto-imports; anything under `app/` that uses `computed/ref` needs explicit `import { ... } from 'vue'` to be testable outside Nuxt.
- Run tests as `pnpm exec vitest run` from repo root.

## Data model

```ts
// shared/types.ts
type Player = { id: string; name: string }
type Match = {
  id: string
  round: number
  playerAId: string
  playerBId: string
  reported?: Report | undefined   // undefined = not yet reported
}
type Report = {
  reporterId: string              // which player submitted this report
  result: 'A_WIN' | 'B_WIN' | 'DRAW'
  touchdownsA: number
  touchdownsB: number
  casualtiesA: number             // casualties inflicted BY player A
  casualtiesB: number
}
type League = { id: string; name: string; players: Player[]; matches: Match[] }
```

Scoring (`shared/scoring.ts`) per player across all reported matches:
```
points = 3*wins + 1*draws ; td = Σ touchdowns ; cas = Σ casualties inflicted
sort: points desc → td desc → cas desc → name asc
```
A match becomes official as soon as ONE report exists (shared ownership — either player logs for both). If both report and they disagree, the later report wins (last-write-wins); the UI warns when overwriting an existing report.

## API routes (Nitro)

| Method | Route | Purpose |
|---|---|---|
| GET | `/api/leagues` | list leagues (id, name, player count) |
| POST | `/api/leagues` | create league `{ name }` |
| GET | `/api/leagues/:id` | full league |
| POST | `/api/leagues/:id/players` | add player `{ name }` |
| POST | `/api/leagues/:id/rounds` | generate next round (pair unpaired players sequentially; odd count → bye for last player, bye = no match recorded) |
| POST | `/api/matches/:matchId/report` | submit report body |
| GET | `/api/leagues/:id/standings` | computed standings |

Persistence: SQLite file `data/bloodtrack.db`, table `leagues(id TEXT PK, json TEXT)` — each league as one JSON blob. Simple, adequate for a local league tool.

## Pages

- `/` — picker: "League Admin" button + list of existing leagues; picking a league lists its players ("play as…"); choice saved to `localStorage` as `bloodtrack.identity = { playerId, leagueId }`.
- `/admin/[leagueId]` — manage players, generate rounds, see fixtures/results per round.
- `/player/[leagueId]` — my matches (current + past rounds); open an owned match to report stats. Includes prominent link to https://bloodbowlbase.ru/bb2025/core_rules/#post-game-sequence .
- `/standings/[leagueId]` — table: Player, P, W, D, L, TD, CAS, Pts (sorted per tiebreakers).
- Logout button (header component when identity exists) clears localStorage → back to `/`.

## Risks / open questions
- **Report conflicts (last-write-wins):** acceptable for v1; alternative is locking after first report.
- **Odd player count:** handled as a bye (no stats awarded) — confirm desired.
- **Data is server-global (anyone can edit anything)** — fine while no auth; localStorage identity is cosmetic, not security.
- **SQLite file location** assumes single-server local deployment; switch later if hosted multi-instance.
